# E-mail-напоминания об окончании подписки

## Назначение и границы

Функция отправляет только добровольно включённые напоминания за 7, 3 и 1 день
до окончания текущей оплаченной конечной подписки. Это не автопродление и не
универсальный API отправки писем. Пользователь может включить или отключить
напоминания в личном кабинете; отключение всегда доступно, даже если SMTP или
глобальная доставка временно недоступны.

## Согласие пользователя

`GET /auth/notification-preferences` возвращает сохранённый opt-in отдельно от
текущей возможности доставки (`email_eligible`). `PATCH` принимает только
явный JSON boolean. Включение допускается только для текущего подтверждённого
e-mail и выполняется одним условным PostgreSQL `UPDATE`.

Момент согласия нельзя вычислять в приложении до захвата строки. При переходе
`false -> true` DAO записывает `clock_timestamp()` внутри атомарного `CASE`
после получения row lock и повторной проверки e-mail, verification, block и
merge-предикатов. При `true -> true` тот же `CASE` сохраняет первоначальный
`enabled_at`; повторный запрос поэтому идемпотентен. Отключение безусловно
записывает `false/NULL`. Ограничения БД дополнительно требуют согласованности
opt-in, `enabled_at`, адреса и verification.

Смена e-mail очищает согласие. При merge согласие source не переносится, а
сохранённое решение target остаётся целевым. Статус verification всегда следует
фактически выбранному адресу: source verification применим, если source e-mail
выбран из-за отсутствия target e-mail или оба аккаунта содержат строго тот же
адрес. Другой адрес при `KEEP_TARGET` сохраняет только target verification.

## Durable outbox и генерация

Генератор запускается ежечасно на 17-й минуте. Он создаёт строки только для
`current_subscription_id`, статуса `ACTIVE`, `is_trial=false`, конечного
`expire_at` и включённого opt-in. Уникальность
`(user, subscription, expire_at snapshot, days_before)` делает генерацию
идемпотентной. Один запуск обрабатывает не более 500 пользователей и создаёт не
более `500 × 3 = 1500` строк. Терминальные строки `SENT/CANCELED/FAILED` старше
90 дней удаляются ежечасно пачками до 3000; cleanup throughput тем самым строго
выше максимальной скорости генерации. Partial index
`(updated_at, id) WHERE state IN (SENT, CANCELED, FAILED)` поддерживает фильтр и
порядок bounded cleanup без сканирования и сортировки active outbox.

Доставка запускается каждую минуту. Допустимое окно — от `due_at` включительно
до `due_at + 1 час` включительно. Более старые active-строки не участвуют в
claim и переводятся в `CANCELED/DELIVERY_WINDOW_EXPIRED` пачками до 500; после
maintenance worker сразу обрабатывает актуальные строки, поэтому старый backlog
их не блокирует.

Worker захватывает ровно одну строку непосредственно перед отправкой через
`FOR UPDATE SKIP LOCKED`. Каждые claim/reclaim увеличивают `attempt_count`;
максимум — 5. Истёкший lease пятой попытки становится
`FAILED/ATTEMPTS_EXHAUSTED` и больше не может быть захвачен.

## Revalidation, SMTP и fenced heartbeat

После claim worker в отдельной короткой транзакции повторно проверяет opt-in,
`enabled_at <= due_at`, подтверждённый e-mail, block/merge, текущую подписку и
точное совпадение `expire_at snapshot`. Неактуальная строка отменяется. Эта
транзакция завершается до сетевого I/O, поэтому SMTP не удерживает блокировки
user/subscription.

SMTP выполняется отдельной async-задачей, а основной coroutine раз в минуту
продлевает десятиминутный lease коротким fenced `UPDATE`. Продление возможно
только для совпадающих `id + PROCESSING + token` и ещё не истёкшего lease;
новое время вычисляется сервером как `clock_timestamp() + 10 минут`. Таким
образом медленная или trickle SMTP-сессия не становится доступной другому
worker. Heartbeat полностью заканчивается до `mark_sent` или `release_failed`.

При временной ошибке БД heartbeat-транзакция откатывается, в лог попадает только
безопасный код типа ошибки, затем выполняется повтор. При потере fence worker
дожидается фактического завершения SMTP, но не изменяет outbox старым token.
`asyncio.timeout` намеренно не используется: отмена coroutine не останавливает
уже работающий `asyncio.to_thread`/smtplib вызов. Успех SMTP и фиксация `SENT`
не могут быть одной транзакцией; узкий риск повтора после crash ограничивает
стабильный `Message-ID`.

`Message-ID` не содержит user, e-mail или открытый outbox PK. Его local-part —
детерминированный HMAC-SHA256 от versioned namespace и reminder id с ключом
`APP_CRYPT_KEY`; допустимый домен берётся из адреса отправителя.

Для implicit TLS и STARTTLS каждый SMTP-вызов создаёт один
`ssl.create_default_context()`. Контекст с `CERT_REQUIRED` и hostname checking
передаётся соответственно в `SMTP_SSL(..., context=...)` или
`starttls(context=...)`. Текущие безопасные логи не содержат адресов и текста
ошибок SMTP. Одновремённые `EMAIL_USE_TLS=true` и `EMAIL_USE_SSL=true`
запрещены. При включённом SMTP отсутствие обоих защищённых режимов также
отклоняется, кроме явного `EMAIL_ALLOW_INSECURE_SMTP=true` — это только
dev-override для локального SMTP sink, поскольку логин и письмо идут открытым
текстом.

## Конфигурация

- `EMAIL_ENABLED` и SMTP-параметры управляют общей e-mail-инфраструктурой.
- `EMAIL_ALLOW_INSECURE_SMTP=false` по умолчанию запрещает plaintext SMTP;
  значение `true` допустимо только для локальной разработки.
- `EMAIL_SUBSCRIPTION_EXPIRATION_REMINDERS_ENABLED=false` — отдельный fail-closed
  kill switch.
- `EMAIL_SUBSCRIPTION_EXPIRATION_CABINET_URL` — явная HTTPS-ссылка обычного
  браузерного кабинета без токенов; URL обязан содержать hostname и не может
  содержать userinfo. Telegram WebApp URL для писем не подходит.

В письме явно сказано, что автопродления нет, уже продливший пользователь может
проигнорировать письмо, а при попадании в спам следует отметить его как
«Не спам» и добавить отправителя в контакты или белый список.

## Миграция, включение и откат

Изменение схемы разделено на две транзакции. `0057` сначала создаёт новую
outbox-таблицу, затем с fail-fast `lock_timeout=2s` добавляет в `users` две
колонки и `CHECK ... NOT VALID`. Краткий `ACCESS EXCLUSIVE` поэтому не ждёт
неограниченно за длинной транзакцией, а существующие строки не сканируются под
этой блокировкой. Новые записи уже обязаны соблюдать ограничения. Отдельная
`0058` выполняет `VALIDATE CONSTRAINT` под `SHARE UPDATE EXCLUSIVE`, который
совместим с обычными `SELECT/INSERT/UPDATE/DELETE`; для него заданы отдельные
`lock_timeout=5s` и `statement_timeout=5min`. Граница надёжна, поскольку Alembic
настроен с `transaction_per_migration=true`.

Перед первым `ALTER users` устанавливается DB-trigger: при смене e-mail или
потере verification он до проверки ограничений атомарно очищает оба consent-
поля. Это защищает также прямые записи и старый runtime, который ещё не знает о
новых колонках, поэтому откат приложения не ломает смену e-mail после opt-in.
Downgrade сначала удаляет trigger, затем его функцию, ограничения и колонки.

Безопасный rollout: применить `0057`/`0058` при работающем старом runtime,
оставить глобальный kill switch выключенным, заменить API и worker, затем
scheduler, проверить backlog/ошибки и только после этого разрешить opt-in и
включить доставку. При откате сначала выключить kill switch и scheduler,
завершить уже поставленные reminder-задачи новым worker, затем вернуть старые
образы. Схему `0058` можно оставить: она additive и DB-trigger сохраняет
совместимость старых операций с e-mail.
